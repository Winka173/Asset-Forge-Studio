# Shared host RAM admission

Single, Batch and revision jobs retain the existing SQLite job graph and GPU/CPU locks. Before admission the worker checks a shared host-memory ledger under the same machine lock root. This is a resource claim, not another queue. One heavy GPU job and the existing bounded CPU slots remain the concurrency limits.

Each stage has a conservative planning allowance. Full TRELLIS.2 starts at 32 GiB host RAM, based on the retained 15.7-million-triangle castle run and room for offload/temporary allocations. Native-checkpoint finishing starts at 10 GiB; SDXL concept at 12 GiB; Blender/Editor stages at 8 GiB. Smaller CPU stages have separate allowances. These are admission estimates, not measured hard model requirements. Two GiB remain as shared headroom. Recorded worker RSS/Windows private peaks can raise subsequent allowances for the same stage/profile; estimates use an additive SQLite drafts namespace and are scoped to the Library. No generation configuration is rewritten.

The ledger subtracts the unrealized portion of active claims from currently available RAM. This prevents a second stage from treating RAM reserved by a model still loading as free. Admission is rechecked under a machine-wide lock when the slot is actually acquired. A memory-held job remains Queued with a timestamped admission receipt and readable pipeline reason. The scheduler keeps considering cheaper independent work. Pause/cancel and manual-restart policy remain authoritative. Queue wait does not consume the active execution timeout.

Claims bind the server PID, process creation time, native thread ID and immutable job folder. Child recognition checks its creation time and command line. Dead claims can be removed; an owned child surviving its owner holds the GPU until it exits. Unreadable/permission-denied claims fail closed for inspection. This guard covers claims created by this version, not arbitrary third-party CUDA processes or legacy apps that never wrote claims. All real native AI acceptance retains the shared GPU lock.

External apps can allocate memory after admission, and stage estimates can be wrong. This reduces overlap risk; it does not guarantee zero OOM or certify artistic quality. Source checkpoints, Maximum settings and existing error recovery remain intact. No memory-saving change to precision, steps, checkpoint, resolution, triangle target or texture budget is made.

Tests in `tests/test_host_resources.py` use controlled RAM readings for admission arithmetic and a real owned child process for orphan handling. `desktop/verify-host-admission.mjs` uses a declared pending-RAM claim as a negative fixture, then real local SDXL concept generation and Blender processing of the retained tower. The fixture allocates no model and claims no successful AI output. Final 0.9.7 acceptance passed: visible wait/no process, Pause/restart/manual Resume, actual SDXL50/1024, real retained-tower Blender/reopening, unchanged quality/source and two jobs without duplication. Evidence: `evidence/host_admission_native_v097.json`. All 145 backend tests, frontend and fresh Windows/generic smoke passed; packaged source cache verified.
